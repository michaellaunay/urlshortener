Changelog
=========

2.0.14 (2026-08-22) — the limiter's identity and its cost (train 0014)
-----------------------------------------------------------------------

- **D-04 (medium, fixed)** The throttling key was the full client
  address. An IPv6 subscriber is handed a **/64** — eighteen billion
  billion addresses — so one machine could take a fresh source address
  per request and the counter never rose. Keys now collapse to the /64
  for IPv6; IPv4 keeps its full address, having no equivalent
  allocation. The form and the API were also using two different key
  functions, so alternating between them doubled the allowance; they
  share one now, and a test asserts they are literally the same
  function.
- **D-03 (low, fixed)** Train 0004 bounded the limiter's memory and
  left a CPU cost behind: every new key at the ceiling swept all 20 000
  entries looking for expired ones, with the lock held — measured at
  0.83 ms per new key, so an attacker rotating source addresses bought
  roughly a thousand times their own cost. The store is now an
  ``OrderedDict`` in least-recently-seen order: eviction pops the
  front, the sweep is gone, and the cost is O(1) amortised. A test
  fails if a new key at the ceiling costs more than 0.1 ms, and another
  checks the key evicted is the idle one rather than the active one.
- **D-05 (low, fixed)** ``PyYAML`` was in no lock, so the two checks
  that actually PARSE ``docker-compose.yaml`` — the service, its
  dockerfile, context and volume, and the loopback-only publishing —
  used ``importorskip`` and skipped silently, on every machine and in
  CI. Two gates that existed and never closed, in the same family as
  the bandit job that failed unnoticed from train 0004. Locked, the
  skips removed, and a test asserts the lock entry so they cannot go
  quiet again.

Also documented: after a patch whose ``git apply`` touched a
``requirements*.lock``, the environment must be reinstalled before the
suite is run. Train 0012 added ``idna`` and the delivery note said only
"apply and test", which turns into a ``ModuleNotFoundError`` that kills
pytest's collection before any test can report anything useful.


2.0.13 (2026-08-22) — cross-site creation (train 0013)
--------------------------------------------------------

- **D-02 (medium, fixed)** A ``POST`` in
  ``application/x-www-form-urlencoded`` is a CORS-SIMPLE request: a
  browser sends it with no preflight and shows the answer to nobody. So
  any third-party page could make its visitors create links, at THEIR
  address — which also spreads the rate limit across strangers — and
  the preflight added in train 0009 stood in front of none of it,
  because a form never preflights.

  There is no session here, so there is no CSRF token. ``Sec-Fetch-Site``
  is the sessionless answer: the browser states where the request came
  from, and a page can neither remove it nor choose its value. An absent
  header passes, deliberately — ``curl`` and every non-browser client
  send none, and refusing them would break far more than it protects.

  **BREAKING, in a v1 API one day old**: ``POST /api/v1/shorten`` now
  requires ``Content-Type: application/json`` and answers 415
  otherwise. Train 0009 documented ``curl -d url=...`` as a
  convenience, and it was one; but that content type is exactly what
  lets a third-party page skip the preflight, and the preflight is
  where ``cors_origins`` is enforced. Requiring JSON is what makes that
  setting mean something. The one-line curl stays one line, with a
  ``-H`` added.

  The guard runs BEFORE the throttle, so a refused cross-site post
  costs a visitor no rate-limit slot — a test pins the ordering rather
  than asserting it.

  Stated rather than left implicit: ``GET /?url=`` remains reachable
  from an ``<img>`` tag, which no header check can distinguish from a
  legitimate navigation. Closing it is ``enable_legacy_get = false``
  (train 0010), a decision with a date rather than a patch. A test
  records that it is still open.


2.0.12 (2026-08-22) — browser-compatible IDNA (train 0012)
-----------------------------------------------------------

- **D-01 (high, fixed)** International host names were encoded with
  Python's built-in ``idna`` codec, which implements RFC 3490
  (IDNA2003). A browser follows the URL Standard, which is UTS #46 with
  NON-TRANSITIONAL processing, and the two disagree on names that
  exist::

      faß.de       stored as fass.de           browser reaches xn--fa-hia.de
      βόλος.com    stored as xn--nxasmq6b.com  browser reaches xn--nxasmm1c.com

  Those are different domains and can have different owners, so the
  service could hand out a short link that resolves somewhere other
  than the address it was given — the one property a shortener has to
  keep. The blocklist was wrong in the same way: an entry written
  ``faß.de`` blocked ``fass.de`` and let the intended domain through.

  Now uses the ``idna`` package with ``uts46=True,
  transitional=False``. Added to ``pyproject.toml`` and to the three
  hashed locks, since replacing a built-in codec adds a dependency and
  an unlocked import fails only in the container.

  This is the same class of defect as the non-ASCII ``Location:`` fixed
  in 2.0.1, and it was introduced by train 0002 — the canonicalisation
  train written to close that class. Hence a test file of its own, and
  a test that asserts what the OLD codec produced, so the difference is
  recorded rather than the preference.

2.0.10 (2026-08-22) — a way out for GET /?url= (train 0010)
------------------------------------------------------------

- **C-09 (medium, made decidable)** ``GET /?url=`` is a GET that
  writes, and three things follow: browser prefetch, crawlers, scanners
  and a plain ``<img src>`` on any third-party page create links, at the
  visitor's address rather than the author's; the target lands in a
  query string and therefore in the access log, the browser history and
  whatever reads either; and no preflight stands between a third-party
  page and it.

  It stays **ON by default**. KuneAgi calls it, and this project's
  first promise is that nothing written against the 2016 service
  breaks. Turning it off by default would be the project breaking its
  own contract to satisfy an audit.

  What is added is the ability to switch it off — new
  ``urlshortener.enable_legacy_get`` — and the means to know when that
  is safe. Every answer now carries ``Deprecation: true`` and a
  ``Link`` to ``POST /api/v1/shorten`` with ``rel="successor-version"``
  (built from ``base_url``, so it stays correct behind a prefix mount),
  and every use logs one line at INFO. Grep that line for a month; when
  it stops appearing, the switch is a decision rather than a gamble.

  Disabled, it answers **410 Gone** — the endpoint existed, and the
  answer is that it is over — keeping the 2016 body shape so an old
  client's parser reads the refusal instead of choking on it. Nothing
  else changes: the home page, the form, the API and the redirect are
  untouched, which a test checks.

  The log line deliberately does NOT repeat the target: it is already
  in the query string of the access log, and writing it a second time
  would put a password-reset URL in a second place for no gain. A test
  pins that.


2.0.9 (2026-08-22) — preflight and start-up validation (train 0009)
--------------------------------------------------------------------

- **C-15 (functional, fixed) — cross-origin access was announced and
  did not work.** Every allowed response advertised
  ``Access-Control-Allow-Methods: GET, POST, OPTIONS`` and no view
  answered ``OPTIONS``, so a browser POSTing JSON — which always
  preflights — received a **404 on the preflight** and never sent the
  request. ``OPTIONS`` is now answered on ``/``, ``/api/v1/shorten``
  and ``/api/v1/links/{code}`` with a 204 plus
  ``Access-Control-Max-Age``. The answer is 204 whatever the origin:
  the permission headers are added only for an allowed one, and a
  browser reading a 204 without them refuses the call itself. A test
  now walks the advertised methods and checks each one is implemented,
  so the mismatch that caused this finding cannot recur.
- **C-15 (low, fixed) — ``Vary: Origin`` on the refusals too.** It was
  set only on the branch that allowed a named origin, so a shared cache
  could store the header-less answer given to a refused origin and hand
  it back to an allowed one, or the reverse. As soon as the answer
  depends on ``Origin``, every answer must say so.
- **C-17 (medium, fixed) — an impossible configuration started
  cleanly.** ``code_length = 0`` was accepted and failed hours later,
  on the first shortening, with a ``ValueError`` about an alphabet.
  ``AppSettings.validate()`` now runs in ``main()`` and refuses to
  start, collecting every problem before raising so one restart shows
  the whole list. It also catches pairs that are each valid and jointly
  impossible — ``max_body_bytes`` below ``max_url_length`` plus the
  envelope means a URL of the allowed length can never be submitted —
  and refuses ``javascript:``/``data:``/``vbscript:`` in
  ``allowed_schemes``. Validation is deliberately NOT run from
  ``__post_init__``: a test building an odd settings object on purpose
  must stay free to do so.
- **Regression from train 0004, fixed.** ``default_gateway`` compared
  an address with the literal ``"0.0.0.0"``; bandit reads that as a
  bind to every interface (B104) and the quality job **exits 1**. It
  had been failing since 0004 — the check ran, and its output was read
  through a grep loose enough to match the wrong line. Rewritten as
  ``ipaddress.IPv4Address(...).is_unspecified``, which is also what it
  meant.


2.0.8 (2026-08-22) — eleven-character codes (train 0008)
---------------------------------------------------------

- Freshly minted codes go from nine to eleven characters, the length of
  a YouTube identifier (``youtu.be/dQw4w9WgXcQ``). Maintainer decision,
  taken one train after 0007 raised 7 to 9.

  62**11 is about 5.2e19, or 65.5 bits. YouTube's alphabet has 64
  symbols and ours 62, so the two sit within half a bit of each other
  (66.0 against 65.5) — and nobody has ever found a YouTube link too
  long to paste.

  With a million links stored, a blind probe now finds one per 52
  trillion attempts, against 13 billion at nine characters and 3.5
  million at seven.

  **Nothing already handed out changes**, including the nine-character
  codes minted between 0007 and this train: length governs codes being
  MINTED, and resolution accepts any legal code whatever its size.

  The ratchet test moves with the default — ``code_length >= 11``, so
  raising it later passes and lowering it fails — and a new test pins
  the length to ``len("dQw4w9WgXcQ")`` and checks the two alphabets
  stay within one bit, so the stated equivalence cannot quietly stop
  being true.


2.0.7 (2026-08-22) — nine-character codes (train 0007)
-------------------------------------------------------

- **C-14 (low, changed)** Freshly minted codes go from seven to nine
  characters: 62**9, about 1.4e16, or 53.6 bits. External audit
  observation, and a maintainer decision — a short code is treated as a
  secret by whoever pastes it, whatever the service promises.

  The figure that justifies it is the hit rate of a blind probe,
  ``stored / 62**length``, not the collision rate, which the retry loop
  absorbs. At seven characters with a million links stored that was one
  hit per 3.5 million probes, within reach of a patient scraper; at
  nine it is one per 13 billion. The cost is two characters. YouTube
  uses eleven, and nobody finds those long.

  **Nothing already handed out changes.** Length governs codes being
  MINTED; resolution accepts any legal code whatever its size, and the
  2016 corpus starts at one character. Short and long codes coexist in
  one table, which is what the import has relied on since 2.0.0.

  A ratchet test asserts ``code_length >= 9`` rather than equality, so
  raising it later passes and lowering it fails, and further tests
  check that the shipped .ini files and the compose default agree with
  the code.


2.0.6 (2026-08-22) — the legacy import (external audit, train 0006)
--------------------------------------------------------------------

- **C-10 (medium, fixed) — an imported code a route already answers
  on.** ``healthz`` is seven characters of the code alphabet, so
  ``is_valid_code`` called it legal and a 2016 row carrying it imported
  cleanly — into a link nobody can ever follow, because ``/healthz`` is
  a route. ``tests/test_routes.py`` already asserted that no route may
  shadow a code; the import was the one door left open. Reported and
  refused rather than renamed: a renamed code is a dead link, and only
  the operator can weigh a dead link against an unreachable one.
- **C-10 (medium, fixed) — the import applied a fraction of the
  policy.** It checked the code, the emptiness, the control characters
  and the scheme, and nothing else, so a migration could reintroduce
  private targets, blocked hosts, invalid ports and over-long URLs that
  the running service refuses. It now judges every row with
  ``normalise_url`` — as a JUDGE, never as a transformer: URLs and
  codes are still stored verbatim, which is the migration contract.

Refusals are now of two kinds, because they call for two different
actions. **Unfixable** rows cannot work or must not work (bad code,
reserved code, empty URL, control characters, and the
``javascript:``/``data:``/``vbscript:`` schemes); no flag lifts them.
**Policy** rows are links that work, which today's rules simply would
not create; ``--allow-unsafe-legacy`` imports them once the operator
has read the list. The flag lifts exactly the policy refusals and never
the others — a flag that can import an XSS vector is not a flag, it is
a trap laid for a future operator in a hurry. The report prints both
lists and tells the operator which action fits which.


2.0.5 (2026-08-22) — request-body limits (external audit, train 0005)
----------------------------------------------------------------------

- **C-04 (high if exposed, fixed)** ``urlshortener.max_url_length``
  capped the URL at 2 KiB and nothing capped the envelope carrying it.
  Waitress leaves ``max_request_body_size`` at its default of **1 GiB**,
  and the compose service is declared ``mem_limit: 512m`` — on paper the
  application accepted a body twice the size of the memory it runs in.

  Capped at 16 KiB in three tiers, driven by ONE value
  (``URLSHORTENER_MAX_BODY_BYTES``) so they cannot drift: waitress
  (``max_request_body_size``, plus ``max_request_header_size`` at
  32 KiB), the application (``urlshortener.max_body_bytes``), and
  ``client_max_body_size`` in the nginx recipe. A test fails when the
  server and the application disagree.

  The application check reads ``Content-Length`` and never touches the
  body — reading a body to discover it is too large IS the denial of
  service — and runs BEFORE the throttle on both creation endpoints, so
  refusing an oversized request costs neither a parse nor a rate-limit
  slot. A request declaring no length (chunked) is left to the server's
  own limit rather than judged on nothing. New ``error_body_too_large``,
  translated into the four languages.


2.0.4 (2026-08-22) — deployment (external audit, train 0004)
-------------------------------------------------------------

- **C-07 (high in effect, fixed) — the compose stack served nothing.**
  ``production.ini`` binds ``localhost:5123``, correct on bare metal and
  unreachable in a container: Docker forwards the published port to the
  container's interface, not to the loopback of its namespace.
  ``URLSHORTENER_LISTEN`` existed in ``.env.example``, in the entrypoint
  and in the override helper — and was passed in by nothing. Every
  connection was refused. Now forwarded, and locked by a test that
  checks every declared override against what compose actually passes.
- **C-07 (medium, fixed) — one address for every visitor.** Inside a
  container ``trusted_proxy = 127.0.0.1`` is not useless but wrong:
  nginx arrives through the Docker bridge, waitress decides the peer is
  not the trusted proxy and ignores ``X-Forwarded-For``, so
  ``client_addr`` is the bridge for everyone and the creation limiter
  becomes one global budget a single visitor can exhaust. The
  entrypoint now reads the default gateway from ``/proc/net/route`` and
  substitutes it, but ONLY when the file still carries the bare-metal
  default; an operator's own value is never overwritten and
  ``URLSHORTENER_TRUSTED_PROXY=none`` trusts nothing.
  ``URLSHORTENER_TRUSTED_PROXY_COUNT`` is forwarded too.
- **C-06 (medium, fixed) — the nginx recipe was wrong twice.** A
  ``location = /`` does not inherit ``proxy_set_header`` from a
  neighbouring ``location /``, so the documented vhost produced exactly
  the failure above; and ``limit_req`` covered ``/`` only, leaving
  ``POST /api/v1/shorten`` — the new creation endpoint — outside the
  limit. The headers now live in an included file, and the limit covers
  every creation path. ``client_max_body_size 16k`` added.
- **C-12 (low, fixed) — the backup.** ``umask 077`` and a 700
  directory, set before anything is written; the dump holds every URL
  ever stored. It no longer copies the database into a ``:memory:``
  connection first, which under ``mem_limit: 512m`` was a time bomb
  proportional to the data. Output is now a consistent SQLite file
  rather than a SQL dump.


2.0.3 (2026-08-22) — the language switcher (external audit, train 0003)
-----------------------------------------------------------------------

- **C-01 (medium, fixed)** Open redirect in ``GET /locale/{locale}``.
  The guard filtered the string: anything starting with ``/`` and not
  with ``//`` was echoed straight into ``Location:``. ``/\evil.example``
  satisfies both conditions, and the URL Standard requires a browser to
  read the backslash as an authority separator, so
  ``new URL('/\evil.example', 'https://good.example/x')`` resolves to
  ``https://evil.example/`` — an open redirect on our own domain, which
  is exactly the domain a phishing page wants to be seen leaving from.

  Fixed by construction rather than by one more string test: the
  parameter is matched against a NAMED ROUTE and the answer is
  regenerated by ``route_path`` from that route's name and matched
  elements. No character the caller supplied can reach the response.
  ``RETURNABLE_ROUTES`` holds the pages one may come back to (today:
  ``home``); ``NON_RETURNABLE_ROUTES`` holds every other route WITH the
  reason, and a test fails on any route that is in neither — so a new
  route forces a decision instead of inheriting a default. ``redirect``
  (``/{code}``) is refused explicitly: it matches everything.


2.0.2 (2026-08-22) — host canonicalisation (external audit, train 0002)
-----------------------------------------------------------------------

Findings C-02, C-08 and C-16 of the external audit, plus a regression
of my own. Tests in ``tests/test_audit_external_20260822.py``.

- **C-02 (medium, fixed)** ``block_private_targets`` was checked with
  ``ipaddress.ip_address()``, which accepts exactly one spelling of an
  address. A browser accepts four: ``http://2130706433/``,
  ``http://127.1/``, ``http://0x7f000001/`` and ``http://0177.0.0.1/``
  were all ACCEPTED and all reach 127.0.0.1. Adds a URL-Standard IPv4
  reader used by the guard. A numeric-looking host that is not a valid
  address (``1.2.3.4.5``) is now refused, as a browser refuses it.
- **C-08 (medium, fixed)** ``blocked_hosts`` compared the raw host, so
  ``bücher.example`` walked past a list containing
  ``xn--bcher-kva.example`` — the same DNS name. Both sides are now
  canonicalised; either spelling blocks both.
- **C-16 (low, fixed) and a 2.0.1 regression** ``parts.port`` is lazy
  and raises on ``:99999`` or ``:abc``. ``to_wire_url`` read it, so my
  own 2.0.1 fix turned a bad port into a **500 at creation**. The port
  is validated up front (new ``error_url_port``, translated into the
  four languages) and ``to_wire_url`` no longer raises on anything —
  it also runs against rows imported verbatim from 2016.

Behaviour widened on purpose: the private-target guard now uses
``is_global`` instead of a hand-kept property list, so the
documentation ranges (``192.0.2/24``, ``198.51.100/24``,
``203.0.113/24``, ``2001:db8::/32``) are refused too when the guard is
on. The canonical host is also what gets STORED, so two spellings of
one target now de-duplicate to a single short code.


2.0.1 (2026-08-22) — internal security audit
--------------------------------------------

Findings and fixes from ``docs/fr/audits/20260822_audit_securite_interne.md``.
One regression test per finding, in ``tests/test_audit_20260822.py``.

- **S-01 (high, fixed)** A target carrying non-ASCII characters was
  stored and served raw in ``Location:``. Waitress encodes the header
  block as latin-1, so such a link answered **500 on every visit, for
  ever** (Japanese, Cyrillic, emoji), or redirected to a MANGLED
  address (latin-1 range). Targets are now stored and served in their
  wire form: IDNA host, percent-encoded path, no double encoding. The
  redirect re-applies it, because rows imported verbatim from 2016
  never went through creation.
- **S-02 (medium, mitigated + accepted)** Imported 2016 codes are one
  to three characters and sequential, so the whole legacy corpus is
  walkable. Added an optional read limit on the JSON API
  (``urlshortener.throttle_max_reads``, 0 by default). Inherent to the
  2016 design; the redirect is never limited.
- **S-03 (medium, fixed)** ``import_legacy`` interpolated the file path
  into a SQLite URI raw, so a path containing ``?`` silently dropped
  ``mode=ro`` from the operator's rollback copy.
- **S-04 (medium, fixed)** The rate limiter's key is the client
  address; the dictionary had no ceiling, so a scan from many addresses
  grew it until the process died. Hard cap with eviction.
- **S-05 (low, fixed)** ``trusted_proxy_count`` is now explicit in
  ``production.ini``: adding a CDN without raising it would hand the
  rate-limiting key to the visitor.
- **S-06 (low, partly applied)** ``cap_drop: ALL`` added to the compose
  service. ``read_only`` documented but deliberately NOT enabled
  untested.
- **S-07 (low, fixed)** The derived ``var/runtime.ini`` may carry a
  database password and lands on the data volume; it is created 0600.
- **S-08 (low, documented exception)** PYSEC-2026-3447 hits setuptools
  81, fixed in 83 — but pyramid 2.1 pins ``setuptools<82``, so the bump
  is impossible without leaving pyramid 2.1. ``pip-audit`` carries one
  named, dated exception; every other advisory still fails the job.
- **S-09 (low, fixed)** The 404 page counted every link in the table,
  so an enumeration scan charged one aggregate per miss and the handler
  itself failed when the database was down.
- **S-11 (low, fixed)** The SQLite pragmas were attached to the
  SQLAlchemy ``Engine`` CLASS at import time, silently reconfiguring
  every other engine in the process. Attached to our engine instead.

Accepted risks, written down rather than fixed: the service is an open
redirector by design (S-12), ``GET /?url=`` writes and carries no CSRF
token (S-10, kept for 2016 clients), and no name is resolved at
creation time, so DNS rebinding is not covered (S-13).


2.0.0 (2026-08-22)
------------------

Complete rewrite of the 2016 Flask service (ecreall/urlshortener). The
public contract is preserved; everything under it changed.

Compatibility kept (locked by tests/test_legacy_compat.py)

- ``GET /?url=<target>`` still answers the same JSON object
  ``{"short_url", "code": "SUCCESS", "original_url"}``.
- ``POST /`` with a form field ``url`` still answers the HTML page.
- ``GET /<code>`` still answers 302 to the target.
- A submitted address with no scheme is still completed with ``http://``.
- The short-code alphabet is unchanged (digits, lowercase, uppercase),
  so every code minted since 2016 remains a legal code.

Compatibility broken, deliberately

- An unknown code now answers **404** instead of 200 with an error
  page. No monitor could previously tell a dead link from a live one.
- A refused URL answers **400** (and 503 / 429 where they apply)
  instead of 200 with ``code: ERROR``. The body shape is unchanged.
- ``Access-Control-Allow-Origin: *`` is no longer sent to everyone.
  Set ``urlshortener.cors_origins`` to restore it (``*`` is still
  expressible).
- The public base of the short links is configuration
  (``urlshortener.base_url``), not the hard-coded ``http://6li.eu/``.

Security

- SQL statements are parameterised. The 2016 code built INSERT and
  SELECT with ``.format()`` on user input.
- Target URLs are validated: scheme allowlist (http/https), no
  credentials in the authority, no control characters, hostname syntax
  checked, literal private/loopback/link-local addresses refused by
  default. ``javascript:``, ``data:`` and ``file:`` were accepted and
  redirected to before.
- Short codes are drawn from ``secrets`` instead of a sequential
  counter, so one code no longer discloses the next.
- Security headers on every response: CSP with ``frame-ancestors
  'none'``, ``X-Content-Type-Options``, ``X-Frame-Options``,
  ``Referrer-Policy: no-referrer`` on the redirect.
- No third-party asset: the 2016 page pulled Bootstrap and Font Awesome
  from maxcdn on every view.
- No IP address is stored. Rate limiting uses an in-memory window.

Added

- JSON API v1: ``POST /api/v1/shorten``, ``GET /api/v1/links/{code}``.
- ``GET /healthz`` with a real database round-trip, used by the
  container health check.
- Interface in English, French, German and Spanish, with a single
  locale registry (``SUPPORTED_LOCALES``) and the remaining EU official
  languages declared but not yet offered.
- Hit counting per link.
- ``tools/import_legacy``: imports the 2016 ``var/urls.db`` verbatim.
- Schema versioning with contiguous upgrade steps.
- Multi-stage Docker image (digest-pinned base, hash-checked lock,
  non-root, health check) and a compose file.
- 170 tests.

Changed

- Pyramid 2.1 + SQLAlchemy 2 + waitress, Python >= 3.11. The 2016
  requirements (Flask 0.10.1, Flask-Cors 2.1.2) no longer install, and
  ``flask.ext.cors`` has not been importable since Flask 0.11.
- Three hash-pinned dependency locks (runtime / test / quality).
